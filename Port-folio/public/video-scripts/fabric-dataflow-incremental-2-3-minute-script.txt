If most rows in a source have not changed, a full refresh spends time and capacity rereading yesterday instead of moving today's updates. This project replaced that pattern with incremental ingestion in Microsoft Fabric. The original problem was repeated full scanning. Every refresh reprocessed unchanged data, which extended the refresh window and made recovery more expensive when a run had to be repeated. The goal was to make each run smaller, observable, and safe to retry. I implemented the solution with Dataflow Gen2 and Fabric data pipelines. A persisted watermark defines the extraction boundary. At the beginning of a run, the process uses that watermark to identify records that are new or have changed since the previous successful load. Parameterized Dataflow Gen2 queries apply the active range so the transformation path works on changes rather than the complete history. The pipeline layer coordinates the workflow. It manages execution order, captures run status, and supports retries. That orchestration matters because incremental loading is not only a source filter. The system must know which boundary was used, whether the load succeeded, and when it is safe to advance the watermark. The documented design keeps that operational state visible and produces repeatable runs. Incremental outputs land in the Fabric Lakehouse, ready for downstream lakehouse use. My contribution as Data Engineer covered the watermark-driven extraction pattern, Dataflow Gen2 parameterization, pipeline orchestration, retry behavior, and run-state logging. Together, those parts create a managed ingestion path rather than a collection of disconnected refreshes. The result is a production Microsoft Fabric pattern that moves new or changed rows instead of repeatedly scanning all data. It also provides observable execution and a safe recovery path through pipeline retries. The portfolio does not record the source system, watermark column, row counts, refresh duration, capacity consumption, or numerical savings. I therefore do not claim a percentage improvement. The verified outcome is the architectural change itself: persisted watermarks constrain extraction, parameterized Dataflows process the active range, pipelines coordinate and record the run, and the Lakehouse receives incremental outputs. That is the practical shift from a costly full-refresh habit to repeatable incremental ETL.
