A streaming pipeline is not production-ready just because events move quickly. It also has to know where to resume after an interruption, preserve enough history to replay an event, and keep malformed records from contaminating analytics. This project created that production path from Azure Event Hubs to Delta Lake. The business need was near-real-time access to operational events. The engineering challenge was to provide that speed without giving up recovery, schema control, or replayability. A direct stream into a final table would make investigation and reprocessing difficult if something changed upstream. I built the ingestion pattern with Databricks Structured Streaming. Azure Event Hubs provides the partitioned event stream, and Spark consumes it in checkpointed micro-batches. The checkpoints retain processing progress so a restarted stream can continue safely instead of treating every run as a new load. I separated raw capture from validated processing. Incoming events are persisted in a raw form so the original payload remains available for replay and investigation. A validation stage then applies schema expectations. Records that do not meet those expectations are isolated through quarantine handling instead of silently entering a downstream analytical table. Valid records move forward through incremental Delta writes or merges. Delta provides the queryable lakehouse store for downstream consumers while the raw layer remains the recovery and evidence path. This separation means downstream teams receive consistent tables without losing the ability to inspect or reprocess the source events. My role as Data Engineer covered the streaming pattern end to end: consuming Event Hub partitions, managing checkpoints, preserving raw events, validating records, handling quarantine, and landing incremental Delta outputs. The result is a production, near-real-time ingestion path that balances delivery speed with operational resilience. The portfolio does not record event volume, partition count, processing latency, trigger interval, or recovery-time measurements, so I do not claim a numerical service level. What is verified is the architecture and behavior: continuous ingestion, restart-safe checkpointing, replayable raw data, schema-aware processing, and consistent Delta tables for analytics. That combination is what turns a moving stream into a dependable data product.
